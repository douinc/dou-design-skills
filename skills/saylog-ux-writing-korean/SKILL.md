# 새록 UX 라이팅 가이드

새록(Saylog)의 UI 문구를 작성·검수하는 스킬입니다. 사용자가 의료 전문가라는 점을 전제로, 친근함보다 **정확성·간결성·전문성**을 우선합니다.

> 이 스킬은 Horace(새록의 옛 이름) UX 라이팅 가이드에서 이어집니다. 원칙은 그대로이고, 제품 표면 세 개와 현재 용어에 맞춰 갱신했습니다.

## 핵심 전제

- **사용자**: 의사·전공의·간호사·PA간호사. 대부분 바쁜 임상 현장에서 모바일로 빠르게 훑어봅니다.
- **제품 표면 셋**: 모바일 앱 · 웹 콘솔 · 새록 라이브(always-on-top 데스크탑). **같은 개념은 세 표면에서 같은 말로 부릅니다** — 표면마다 다르게 부르면 같은 제품으로 읽히지 않습니다.
- **톤**: 과도한 친근함(모든 문장 해요체화, 이모지, 감탄사, "잠시만요~")은 배제. 정보 전달 중심의 간결한 전문어 톤을 유지합니다.
- **의료 용어**: 임상에서 통용되는 표기를 그대로 유지합니다(POD, HOD, EMR, SOAP, STT, 직번, 병동, 진료과 등).

## 사용 시기

- 타이틀·디스크립션 문구가 주어졌을 때 (자동 적용)
- 앱·웹 콘솔·새록 라이브·알림·에러 메시지·온보딩 문구를 작성하거나 교정할 때
- 서식명·설정 레이블 등 기능 라벨을 정할 때
- 임상 사용자의 오해·혼동을 줄이기 위해 표현을 다듬을 때
- **이미 출고된 화면의 문구를 바꾸게 될 때** — 이땐 아래 `기존 문구 대조`를 먼저 수행합니다

## 기존 문구 대조 — 문구를 쓰기 전에 (필수)

새 문구를 짓기 전에 **이미 그 자리에 있는 말**부터 찾습니다. 이 단계가 없으면, 원칙을 아무리 잘 지켜도 출고된 앱과 다른 말이 나옵니다. 그러면 개발자는 "이거 의도한 변경이냐"고 되묻게 되고, 확인은 결국 사람 시간으로 치릅니다.

디자인 작업은 보통 화면 몇 개만 건드립니다. 그래서 대조도 **두 겹**이면 충분합니다.

| 겹 | 무엇을 확인하나 | 어떻게 |
| --- | --- | --- |
| 1겹 — 같은 자리 | 지금 고치는 화면에 이미 쓰이는 문구 | 실제 구현 소스와 baseline 캡처에서 그 화면을 찾아 문구를 그대로 읽는다 |
| 2겹 — 같은 개념 | 이 화면에 **새로 등장하는 개념**을 다른 화면은 뭐라고 부르는지 | 제품 소스 전체를 검색한다(개념어로 grep) |

- 실제 구현 소스와 캡처의 위치는 제품 리포의 `docs/design-harness.md`가 가리킵니다. 새록은 `carevoice`의 `flutter/` · `web/` · `saylog-live/`와 `public/{mobile,desktop}/baseline/`입니다.
- **1겹에서 문구를 찾았으면 그것이 기본값입니다.** 바꿀 이유가 있을 때만 바꿉니다. 원칙에 어긋난다는 것도 바꿀 이유가 되지만, 그건 판단이지 자동 교체가 아닙니다.
- **2겹은 화면 하나당 몇 개 안 됩니다** — 버튼 라벨, 상태 이름, 빈 화면 문구 정도입니다. 예를 들어 스토어 상세에 "갱신"을 새로 쓰려 한다면, 기록 화면이 같은 개념을 "다시 생성"이라 부르고 있지 않은지 먼저 찾습니다. 다르게 부르고 있으면 맞추거나, 바꿀 이유를 적습니다.
- 대조 대상이 아예 없는 새 화면의 새 문구는 그냥 아래 원칙대로 씁니다.

**미리 만든 문구 사전을 두지 않습니다.** 사전은 앱이 문구를 바꾸는 순간 거짓말을 시작하고, 그때부터는 사전 자체가 어긋남의 원인이 됩니다. 매번 소스를 찾는 편이 느려 보여도 항상 맞습니다.

### 바꾼 문구는 목록으로 남깁니다

대조 결과 기존과 달라진 문구는 모아 둡니다. 이 목록은 담당자 확인과 개발 핸드오프 양쪽에서 쓰입니다 — 적어두지 않으면 확인받을 방법이 없습니다.

| 자리 | 기존 앱 | 변경안 | 이유 |
| --- | --- | --- | --- |
| 스토어 상세 CTA | 이미 추가됨 — 한 번 더 추가 | 최신 내용으로 갱신 | 중복 설치와 갱신이 구분되지 않음 |

달라진 문구가 없으면 표를 만들지 않습니다. **아무 말도 없으면 "기존 그대로"라는 뜻**이어야, 읽는 사람이 표가 없는 것만으로 안심할 수 있습니다.

## 핵심 원칙

### 1. 종결 어미 — 문구 기능에 따라 구분

무조건 해요체로 통일하지 않습니다. 문구가 **무슨 일을 하는지**에 따라 종결을 선택합니다.

| 상황 | 권장 종결 | 예시 |
| --- | --- | --- |
| 상태·진행 표시 | 명사형 또는 간결한 서술형 | `녹음 중`, `요약 생성 중`, `업로드 완료` |
| 버튼·CTA | 동사 원형 | `녹음 시작`, `요약 생성`, `환자 등록` |
| 상태 라벨/뱃지 | 명사형 | `요약 대기`, `연동 실패`, `POD 3` |
| 안내·설명 문장 | 해요체 (과한 친근함 지양) | `요약은 녹음 종료 후 자동으로 생성돼요` |
| 에러·제한 안내 | 해요체 + 해결 경로 | `파일이 업로드 크기 상한을 넘었어요. 길이를 줄여 다시 시도해 주세요` |
| 법적·정책 문구 | 합니다체 허용 | `녹음 데이터는 개인정보처리방침에 따라 보관됩니다` |

| X (과한 친근함) | O (새록 톤) |
| --- | --- |
| 녹음을 시작해볼까요? | 녹음 시작 |
| 와! 요약이 완성됐어요 🎉 | 요약 생성 완료 |
| 환자를 등록해주시겠어요? | 환자 등록 |
| 잠시만요, 열심히 요약 중이에요! | 요약 생성 중 · 약 30초 |

**예외 — 대화 유도형 진입 문구**: 채팅·도움 흐름으로 이끄는 **공감형 진입 버튼**은 해요체 질문형을 씁니다. 예: `요약이 이상한가요?` 여기서 명사형을 쓰면 버튼이 아니라 상태 라벨로 읽혀서 눌러지지 않습니다. 단 라벨·상태·액션 문구는 위 표를 그대로 따릅니다.

**합니다체는 법적·정책 문구에만 씁니다.** 출고된 화면에 `요약 템플릿을 불러오는 중입니다…`처럼 합니다체 안내가 섞여 있는데, 이건 맞춰야 할 기준이 아니라 정리 대상입니다. 그 화면을 만지게 되면 해요체나 명사형으로 옮기되, 기존 문구를 바꾸는 것이므로 위 `기존 문구 대조`의 변경 목록에 올립니다.

### 2. 의료·도메인 용어는 원형 유지

임상 사용자가 한눈에 식별할 수 있도록 영문·한자어 표기를 보존합니다. 불필요한 풀어쓰기는 가독성을 떨어뜨립니다.

| X (과한 풀어쓰기) | O (도메인 유지) |
| --- | --- |
| 수술 후 경과일 3일 | POD 3 |
| 전자의무기록 연동 | EMR 연동 |
| 주관적/객관적/평가/계획 요약 | SOAP |
| 병원 직원 번호 | 직번 |
| 음성을 글로 바꾸기 | STT |
| 내과·외과 같은 진료 분야 | 진료과 |

> **예외**: 비전문가 접근 화면(마케팅 페이지, 최초 온보딩 첫 노출 등)에서는 한 번만 풀이를 병기할 수 있어요. 예: `EMR(전자의무기록)`.

### 3. 능동·직접 표현

수동·우회 표현을 피하고, 동작의 주체를 드러냅니다.

| X | O |
| --- | --- |
| 녹음이 저장됐어요 | 녹음을 저장했어요 |
| 환자가 등록되었습니다 | 환자를 등록했어요 |
| 요약이 생성될 예정입니다 | 요약 생성 중 |
| 파일이 업로드되지 않았습니다 | 파일을 업로드하지 못했어요 |

**예외 — 수동형 유지**: 사용자 행동의 결과·정책·안심 안내에서는 수동형이 인과를 명확히 합니다.

- `녹음 데이터는 종료 후 암호화돼요` (안심)
- `구독을 해지하면 업로드된 녹음은 {보관 기간}간 보관돼요` (정책 결과)
- `무료 체험 기간이 곧 만료돼요` (기간 종료)

### 4. 긍정형·해결 경로 우선

부정형(`없어요`, `실패`, `불가`)으로만 끝내지 않고, 다음에 무엇을 할지 안내합니다.

| X | O |
| --- | --- |
| 검색 결과가 없어요 | 다른 환자명·차트번호로 검색해 보세요 |
| 네트워크 오류가 발생했어요 | 연결을 확인하고 다시 시도해 주세요 |
| 요약 생성 실패 | 요약을 다시 생성해 주세요 |
| 저장 공간이 부족해요 | 오래된 녹음을 정리하면 업로드할 수 있어요 |

**예외 — 부정형 유지**: 임상 안전·권한·제한처럼 단정적 안내가 필요한 상황.

- `EMR에서 가져온 환자는 새록에서 수정할 수 없어요` (권한)
- `일반 사용자는 환자를 최대 {N}명까지만 등록할 수 있어요` (제한)
- `녹음 원본은 서버에 저장되지 않아요` (안심)

### 5. 경어 — 의료진 간 실무 톤

의료진 대상 제품이므로 과도한 경어(`~시겠어요`, `~해 주시겠습니까`, `~하실게요`)는 생략합니다. 다만 **파괴적 동작·민감 권한·법적 동의**에서는 예의를 갖춥니다.

| 상황 | 톤 | 예시 |
| --- | --- | --- |
| 일반 기능 조작 | 경어 생략 | `확인`, `저장`, `환자 선택` |
| 파괴적 동작(삭제·초기화) | 정중한 해요체 | `환자를 삭제하면 관련 녹음도 같이 삭제돼요. 삭제할까요?` |
| 민감 권한·업로드 | 정중한 해요체 | `이 환자의 녹음 파일을 업로드할까요?` |
| 법적 동의 | 합니다체 허용 | `개인정보 수집·이용에 동의합니다` |

| X | O |
| --- | --- |
| 회원님이 선택하신 서식이에요 | 선택한 서식 |
| 확인하시겠습니까? | 확인할까요? |
| 이 주소가 맞으신가요? | 이 주소가 맞나요? |

### 6. 명사 조합은 상태 라벨에서만 허용

짧은 상태 뱃지·라벨에서는 한자어 명사 나열을 허용하지만, 문장형 안내에서는 동작 기반으로 풀어 씁니다.

| 맥락 | X | O |
| --- | --- | --- |
| 상태 뱃지 (2–4어절) | — | `요약 대기`, `업로드 실패` (허용) |
| 설명 문장 | 파일 업로드 실패 사유 확인 필요 | 파일을 업로드하지 못했어요. 형식과 크기를 확인해 주세요 |
| 에러 안내 | EMR 연동 오류 발생 | EMR과 연결되지 않아서 환자 정보를 가져오지 못했어요 |

## 새록 특화 표기 규칙

### 기능·객체 이름

이름이 흔들리기 쉬운 자리들입니다. 여기가 어긋나면 사용자는 다른 기능이라고 생각합니다.

| 개념 | 쓰는 말 | 쓰지 않는 말 |
| --- | --- | --- |
| AI 요약의 형식 정의 | `서식`, 문맥이 필요하면 `요약 서식` | `기록 서식`, `템플릿`, `양식` |
| 데스크탑 앱 | `새록 라이브` | `라이브 앱`, `데스크탑 앱`(제품명 자리에서) |
| 서식을 주고받는 곳 | `서식 스토어` | `마켓`, `템플릿 스토어` |

**`녹음`·`기록`·`환자`는 서로 다른 것입니다.** 원본 녹음, 그 녹음으로 만든 기록, 기록에 연결된 환자는 분리된 객체이고 화면에서도 그렇게 읽혀야 합니다. `녹음 삭제`와 `기록 삭제`는 다른 일이므로 바꿔 쓰지 않습니다. 특히 **`환자 미지정`을 실제 환자나 가상 환자처럼 부르지 않습니다** — `미연결`, `환자 미연결`처럼 상태로 씁니다.

### 사용자 호칭

- 앱 내부: `회원님` 대신 2인칭 생략 또는 역할 기반 표현 — `등록한 환자`, `내 녹음`, `내 서식`
- 일반 안내·약관: `의료진`, `사용자` (법적 문맥)
- **`선생님`은 사용하지 않아요** — 전공의·간호사·PA간호사를 포괄하지 못하고, 직무 간 위계 인상을 줄 수 있어요.

### 환자 정보 표기

- 환자명은 그대로 노출. 마스킹이 필요하면 `김○○(56세/남)` 형식
- 차트번호·병동·진료과는 축약 없이 원형 유지
- 환자 식별 우선순위: `차트번호 > 이름 > 병동/진료과`

### 날짜·시간

- 임상 맥락: 경과일과 달력 날짜 병기 허용 — `POD 3 · 2026-04-14`
- 상대 표현(`오늘`, `어제`, `3일 전`)은 해요체 안내 문장 안에서만 사용
- 절대 날짜: `YYYY-MM-DD` 또는 `2026년 4월 14일`

### 수량·제한 안내

제한이 있을 땐 **숫자를 먼저, 이유·현재 상태를 뒤에** 붙여 한눈에 파악되게 합니다.

| X | O |
| --- | --- |
| 환자를 더 이상 추가할 수 없어요 | 환자는 최대 {N}명까지 등록할 수 있어요 (현재 {N}/{N}) |
| 녹음 용량이 부족해요 | 녹음 파일은 {크기}까지 업로드할 수 있어요 |
| 녹음 횟수가 초과됐어요 | 환자당 녹음은 최대 {N}회까지 남길 수 있어요 |

**실제 상한값은 이 문서에 적지 않습니다.** 등록 한도·업로드 크기·보관 기간 같은 값은 정책 문서와 구현이 들고 있고 바뀝니다. 여기 박아 두면 값이 바뀐 뒤에도 이 문서가 옛 숫자를 계속 가르치게 됩니다 — 문구 사전을 두지 않는 이유와 같습니다. 문구를 쓸 때 제품 정책 문서나 구현에서 현재 값을 찾아 채웁니다.

### 버튼 라벨

- 동사 우선, 2–4음절, 조사 생략: `저장`, `삭제`, `녹음 시작`, `요약 보기`
- 대화상자 버튼은 약함 → 강함 순: `취소 / 나중에 / 삭제`

### 권한·조회 범위

사용자 유형과 조회 범위를 혼동하지 않도록 표현을 구분합니다.

| 개념 | 권장 표현 |
| --- | --- |
| 전체 환자 조회 권한 | `병원 전체 환자` 또는 `같은 병원의 모든 환자` |
| 개인 환자 조회 권한 | `내가 등록한 환자` 또는 `담당 환자` |
| 주치의 | `주치의` (원형 유지) |
| 녹음 생성자 | `녹음을 남긴 사람` |

## 검수 체크리스트

다음 순서로 확인합니다.

0. **기존 문구를 대조했는가** — 같은 자리의 기존 문구와 같은 개념의 다른 화면 표현을 찾아봤는지. 달라진 게 있으면 변경 목록에 올렸는지
1. **맥락에 맞는 종결인가** — 상태는 명사형, 버튼은 동사, 안내는 해요체
2. **의료 용어가 보존됐는가** — POD/HOD/EMR/SOAP/STT/직번 등 원형 유지
3. **핵심 정보가 앞에 있는가** — 의료진은 빠르게 스캔. 중요 정보를 첫 어절에
4. **능동·직접 표현인가** — 행위 주체가 드러나는지
5. **긍정·해결 경로가 있는가** — 부정형으로 끝나지 않는지
6. **경어 수준이 적절한가** — 과공손(`~시겠어요`)·과친근(`~해볼까요?`) 둘 다 없는지
7. **사용자 유형·권한 표현이 정확한가** — 일반/병원 사용자, 조회 범위, 주치의/생성자 구분
8. **예외에 해당하는가** — 수동형·부정형·합니다체가 필요한 맥락인지
